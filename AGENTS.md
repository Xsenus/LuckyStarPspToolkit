# Правила дальнейшей разработки

1. Перед новой итерацией определить последнюю реально существующую версию по `VERSION`, Git, исходникам и результатам тестов.
2. Minor-версию повышать только за содержательную новую возможность. Patch-версию использовать только для исправлений.
3. Не считать формат проверенным на игре без соответствующего файла заказчика.
4. Не добавлять оригинальные ISO, EBOOT, CPK, PMF, BIN, шрифты и перевод в Git.
5. Любая запись в EBOOT требует полного SHA-256 либо явно утверждённого профиля и точных preconditions.
6. Любой parser обязан проверять границы, переполнения, дублированные endian-поля и разумные лимиты.
7. ISO-парсер не должен доверять размеру тома, каталожным циклам, multi-extent цепочкам, именам или количеству записей.
8. Извлечение из ISO и создание ZIP выполняются потоково; нельзя загружать полный образ или крупный ресурс в память без явного лимита.
9. Пользовательские выходы пишутся атомарно. При ошибке существующий файл должен быть восстановлен либо сохранён аварийный `.bak`.
10. Не добавлять runtime NuGet dependency без документированного обоснования.
11. Комментарии объясняют формат и инварианты, а не повторяют синтаксис.
12. Перед релизом выполнить `scripts/build.*`, автономные тесты, независимые oracles и интеграционный тест с приватными файлами.
13. Релизный отчёт должен отдельно перечислять выполненные, заблокированные и не выполнявшиеся проверки.
14. Все именованные C# типы, методы, конструкторы и локальные функции обязаны иметь XML-документацию; проверять `document_csharp.py --check`.
15. GitHub workflow, release script и README не должны объявлять skipped-проверку успешно пройденной.
16. Сгенерированный `docs/API_REFERENCE.md` обязан совпадать с исходниками.
17. Любой новый внешний код требует явной совместимой лицензии и записи в `THIRD_PARTY_NOTICES.md`.
18. Перед публикацией сканировать архивы на оригинальные игровые файлы, секреты, небезопасные ZIP-пути и неподтверждённые исполняемые файлы.
