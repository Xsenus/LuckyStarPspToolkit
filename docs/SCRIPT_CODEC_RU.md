# Сценарный кодек 0.12.0: границы, перенос адресов и память

## Область изменения

Изменены `LuckyStarScript.cs`, `LuckyStarScript.Build.cs`, новый `ScriptOffsetMap.cs`
и лимиты `FileLimits`. Контракт команд CLI и JSON рабочего пространства не менялся.
Это развитие той же кодовой базы, а не замена проекта новым каркасом.

## Исправленные ошибки

В 0.11.0 каждый диалог помечался изменённым при каждой сборке, даже без правок.
Из-за этого допустимый переход внутрь неизменённого текста мог вызвать
`SCRIPT_JUMP_INSIDE_TEXT`. Теперь изменяемыми считаются только записи, байты которых
действительно отличаются. Без изменений возвращается отдельная побайтно идентичная
копия корректного исходника. В том числе сохраняется файл, выровненный только на
16 байт, даже если обычное выравнивание профиля равно 4096.

Старый цикл сообщения мог прочитать финальный checksum как продолжение текста и
найти в нём ложный терминатор. Новый парсер устанавливает жёсткую границу по
следующей физической записи или началу checksum. В тесте специально создан файл
с **правильным** checksum, который начинается с `0xFFFB`: отсутствие настоящего
терминатора всё равно даёт `SCRIPT_GLYPH_EOF`.

Слишком большой uint32 offset раньше мог приводить к необработанному
`OverflowException`. Новые границы сначала рассчитываются в Int64 и проверяются,
а только затем преобразуются в Int32. Таблицы метаданных не могут перекрывать
друг друга, фиксированный заголовок, jump table или checksum.

## Чтение

Сначала проверяются размер, конфигурация профиля и checksum. Затем проверяются все
таблицы, все jump targets и все начала текстовых записей. Дубли offset отклоняются
**до чтения содержимого**, чтобы одна длинная строка не материализовалась повторно
по множеству ссылок. Текст читается в физическом порядке с ограничением на конец
каждой записи, но модели возвращаются в исходном порядке таблиц.

Перед выделением массива глифов поле сканируется на терминатор и лимиты. После этого
выделяется массив точного размера. Нулевое слово, на которое ссылается переход,
сохраняется как содержимое, а не отбрасывается как padding.

Сценарии без текстовых записей допускают нулевые offsets пустых таблиц. Это покрыто
отдельными синтетическими тестами RGO/NIM, но не означает проверку всех настоящих
сценариев второй игры.

## Сборка

Сначала проверяются ключи изменений, структурные коды и суммарный размер результата.
Изменения описываются небольшими планами; сериализованные копии всех реплик не
создаются. После проверки размера выделяется один итоговый byte[]: неизменённые
диапазоны копируются через Span, изменённые слова записываются прямо в результат.

Таблица соответствия offsets строится по реально изменённым диапазонам. Вместо
повторного линейного поиска по всем диапазонам для каждого перехода используется
binary search по правой границе исходного диапазона. Стоимость каждого запроса —
O(log M), где M — число диапазонов. На разделяемых границах сохранено прежнее
предпочтение левого диапазона, включая anchor пустого варианта ответа.

Переход **внутрь действительно изменённой записи** по-прежнему отклоняется: кодек
не угадывает семантику неизвестной инструкции и не обещает безопасный перенос
произвольного адреса внутрь нового текста. Пустой choice сохраняет anchor перед
вставленным текстом. Эти правила проверяются отдельным линейным эталоном.

После записи offsets и checksum результат снова полностью разбирается. Проверяются
число записей, ID, глифы, терминаторы, группы и варианты выбора. Работа с диском
остаётся обязанностью существующего транзакционного workspace/CLI слоя.

## Лимиты

| Параметр FileLimits | По умолчанию | Когда проверяется |
|---|---:|---|
| MaximumScriptBytes | 67 108 864 байта | До копии исходника и до итогового буфера |
| MaximumScriptFieldGlyphs | 1 000 000 слов | До выделения одного speaker/message/choice |
| MaximumScriptGlyphs | 8 000 000 слов | Совокупно для сценария до выделения массивов |

Продолжают действовать MaximumInputBytes и лимиты таблиц/диалогов/переходов.
Лимиты — защитные пределы, а не гарантия соответствующего RSS процесса или
совместимости огромного сценария с памятью PSP. Увеличивать их нужно осознанно
через API. Для реальной игры дополнительно проверяются EBOOT heap и экранные
ограничения; эту приёмку синтетический тест не заменяет.

## Ошибки для автоматизации

`SCRIPT_INPUT_LIMIT`, `SCRIPT_OUTPUT_LIMIT`, `SCRIPT_FIELD_LIMIT`,
`SCRIPT_GLYPH_LIMIT`, `SCRIPT_BUILD_COUNT_LIMIT`, `SCRIPT_TABLE_RANGE`,
`SCRIPT_TABLE_OVERLAP`, `SCRIPT_JUMP_RANGE`, `SCRIPT_DUPLICATE_TEXT_OFFSET`,
`SCRIPT_OFFSET`, `SCRIPT_GLYPH_EOF`, `SCRIPT_MUTATION_TERMINATOR`,
`SCRIPT_MUTATION_NULL`, `SCRIPT_JUMP_INSIDE_TEXT`.

Это дополнительные стабильные коды подкласса ToolkitException. Некорректные
файлы не следует исправлять отключением checksum или заменой кода возврата на 0.
Приложение не является потокобезопасным редактором одновременно изменяемой модели:
не модифицируйте разобранные коллекции и ScriptMutation параллельно со сборкой.

## Регрессионная проверка

Выполняются 13 новых групп C#-тестов: no-op и неизменённые переходы, границы checksum
и записей, метаданные, дубли/alignment, бюджеты, прямые изменения API, пустые choices,
переставленные таблицы, RGO/NIM, независимый linear-map oracle, 8192 диалога и
1024 мутации заголовка. Полный набор прежних проверок сохранён.

Для штатной среды .NET 9:

```powershell
dotnet run --project tests/LuckyStarPspToolkit.Formats.SelfTests -c Release
```

Для измерения, отдельно от обязательных тестов:

```powershell
dotnet run --project tests/LuckyStarPspToolkit.Formats.SelfTests -c Release -- --script-benchmark
```

Измерение использует синтетические сценарии и не доказывает скорость на исходных
файлах заказчика. Методика сравнения версий — в PERFORMANCE_RU.md.
