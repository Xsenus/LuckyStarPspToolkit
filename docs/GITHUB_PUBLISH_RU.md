# Подготовка и публикация на GitHub — 0.10.0

## До публикации

Сначала проверьте THIRD_PARTY_NOTICES.md и LICENSING.md. Для исходного VWF-профиля и некоторых технических заимствований пока нет подтверждённой цепочки разрешений. Эта поставка не сертифицирует юридическую чистоту всего исторического происхождения. Начните с приватного репозитория; решение о публичном распространении принимайте после проверки прав. Оригиналы игр, переводы и шрифты в репозиторий не добавляются.

В едином архиве папка `project` — чистый снимок исходников без `.git` и бинарных эталонов. Бинарные fixtures генерируются локально. Публичную историю можно начать с этого снимка. Разработка действительно продолжается от 0.9.0; идентификаторы и текстовый diff находятся в отчётах. Не используйте `git push --mirror` старой приватной истории вслепую.

## Публикация чистого исходного снимка

Создайте пустой приватный репозиторий в своём аккаунте. Затем в папке `project`:

```bash
git init -b main
git add .
git status --short
git diff --cached --stat
git diff --cached
python validation/audit_repository.py
git commit -m "Prepare LuckyStarPspToolkit 0.10.0 engineering preview"
git remote add origin <URL_вашего_репозитория>
git push -u origin main
```

Если репозиторий уже восстановлен из чистого snapshot bundle, `git init` и первый commit не нужны. Проверьте ветку и удалите локальный bundle remote, затем добавьте свой origin. Snapshot bundle, если включён в комплект, не называется полной старой историей: старые бинарные эталоны не переносятся в публикацию.

## Проверка CI

Откройте вкладку Actions → `build-test-package`. Нужны зелёные **оба** job: Windows/win-x64 и Linux/linux-x64. В их артефактах лежат фактически собранные ZIP, SHA-256 и журналы. При красном job откройте `logs-<rid>`, исправьте причину, повторите push. Не создавайте customer-ready объявление до успеха реальных проверок.

GitHub Actions использует GITHUB_TOKEN для собственного репозитория; личный токен в коде не нужен. Финальный release job требует `contents: write`, прочие job — только `read`. На fork pull request права ограничены, публикация релиза там не выполняется.

## Выпуск версии

После успешного CI и ручной проверки демонстрации:

```bash
git tag -a v0.10.0 -m "0.10.0 engineering preview"
git push origin v0.10.0
```

Тег обязан совпадать с `VERSION`. Release workflow заново выполняет нативные проверки обеих платформ, после чего создаёт **draft prerelease** с пакетами. Откройте Releases, изучите draft, приложите фактический список ограничений. Публикация draft пользователем — отдельное действие. Stable-релиз не создаётся автоматически: запуск синтетики не означает приёмку обеих игр.

## Последующие версии

Меняйте `VERSION` и четыре version-поля `Directory.Build.props` согласованно; обновляйте CHANGELOG, инструкции, API reference и тесты. Пользуйтесь обычным коммитом и новым тегом. Старые теги не передвигайте задним числом. Сохраняйте лог CI и хэши пакетов вместе с отметкой о проверенной ревизии игры.
