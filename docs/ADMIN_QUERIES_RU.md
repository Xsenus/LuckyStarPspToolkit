# Серверные страницы админки · 0.18.0

## Что изменилось для владельца

В 0.17.0 браузер получал полный список лицензий вместе с массивами установок, хотя
показывал только 25 строк. Раздел резервов отрисовывал только первые 200 элементов.
В 0.18.0 поиск, фильтрация и выбор страницы выполняются сервером. В браузер поступают
только нужные строки. История допусков больше не обрезается первыми 200 элементами.

Откройте «Лицензии», введите часть метки/UUID, выберите статус и нажмите
«Применить фильтры». «Назад» и «Далее» перемещают по 25 строкам. Карточка «Открыть»
загружает установки одной выбранной лицензии отдельным запросом. Верхние счётчики —
вся база, а «Найдено» — количество совпадений с фильтрами, не количество видимых строк.
Поиск буквальный, без регулярных выражений, без учёта регистра; максимум 120 символов.

В «Резервном доступе» отдельно перелистывается история допусков и поиск подходящей
лицензии. Выбор лицензий ограничен активными и уже активированными установками.
Выберите лицензию, затем конкретную установку и срок. Обычные правила 1–168 часов,
проверки родительской лицензии, MFA, CSRF и отзывов не изменились.

## Согласованность страниц

Порядок: CreatedAt по убыванию, при равенстве ID по ordinal-возрастанию. Внутри одной
UTC-секунды порядковый номер выдачи не моделируется; UUID даёт устойчивый tie-breaker.
Курсор хранит исключительную последнюю позицию, а не номер SQL OFFSET.

При первой странице фиксируются ревизия базы и UTC. Следующие страницы оценивают
истечение лицензий относительно той же UTC. Так строка не меняет фильтр прямо между
страницами только из-за хода часов. Страница информационная: команды изменения и
клиентская авторизация всегда повторно проверяются по текущему серверному времени.

Курсор действует строго меньше 120 секунд от первого снимка. Следующая страница не
продлевает срок. Любое зафиксированное изменение базы аннулирует продолжение. Ключ
HMAC живёт только в процессе, поэтому перезапуск сервера также требует новой первой
страницы. Строки или снимки всей базы на сервере для курсоров не сохраняются.

Если база изменилась или курсор истёк, React ровно один раз запрашивает первую страницу
и показывает уведомление. При обычной сетевой ошибке прежняя страница остаётся видна
вместе с ошибкой; ложного успешного перехода нет. Запоздавший ответ старого фильтра или
уничтоженного компонента не заменяет новый результат. Автоматического фонового poll,
который удерживал бы idle-сессию, нет. Кнопка «Обновить» начинает новый снимок.

## Контракт API

Все новые операции — POST на том же owner-origin, с действующей HttpOnly-сессией,
проверкой Origin и X-CSRF-Token. Курсор не является токеном входа и не даёт авторизацию.
Идентификаторы и фильтры не помещаются в URL/query string. Тело читается существующим
ограниченным strict-JSON обработчиком: неизвестные/дублирующиеся поля отвергаются.

```text
POST /api/licenses/query
POST /api/license/get
POST /api/reserve/query
```

Пример первой страницы:

```json
{"limit":25,"search":"Тест","status":"active","cursor":"","activatedOnly":false}
```

Следующая страница повторяет все фильтры и limit, подставляя полученный nextCursor.
Пустой nextCursor означает конец. Нельзя использовать курсор другого endpoint,
поиска, статуса, activatedOnly или размера страницы. Запрос деталей:

```json
{"id":"00000000-0000-0000-0000-000000000001"}
```

Ограничения: limit 1–100; search до 120 символов без управляющих кодов;
внешний курсор до 2048 символов, полезная часть до 1024 байт. MAC проверяется
constant-time сравнением до десериализации. Курсор содержит домен endpoint,
SHA-256 запроса без cursor, ревизию, исходную UTC и последнюю пару CreatedAt/ID.
Ни секретов, ни access-key, ни ключей установок в нём нет. Курсор подписан, не зашифрован.

Ответ лицензий: items/total/nextCursor/revision/asOfUtc/counts. В items отсутствуют
массивы устройств, publicKey, hostBinding и ключи доступа. DeviceCount — число установок.
Подробности возвращаются только точным lookup одной лицензии (лимит установок из
существующей модели, максимум 100). Это уменьшение объёма данных, а не новая роль ACL:
владелец по-прежнему имеет право смотреть детали.

Ответ резервов: items/total/nextCursor/revision/asOfUtc/policy. policy не включает всю
историю. Из ответа изменения общего выключателя массив истории также удалён.
Совместимые старые GET-list endpoints и административная CLI сохранены, но новая
React-панель их больше не использует. Они не стали автоматически потоковыми.

Ошибки: OWNER_PAGE_QUERY — неверный запрос; OWNER_PAGE_CURSOR — подмена/смена
фильтра или неизвестный после рестарта курсор; OWNER_PAGE_STALE (HTTP 409) — ревизия
или срок снимка изменились. Клиент допускает автоматический reset только при переходе
с непустым курсором. Неожиданная ошибка первой страницы не маскируется циклом повторов.

## Статусы резерва

available — текущая политика, поколение, лицензия и установка допускают обновление;
revoked — явный отзыв; retired — выключенная политика или старое поколение;
inactive-license — родительская лицензия неактивна/истекла; missing-device — нет установки.
Приоритет проверки именно такой. Это пригодность к будущему обновлению, а не факт
работы удалённого компьютера. Уже отключённый клиент всё ещё ограничен ранее выданным
подписанным TTL; мгновенный дистанционный отзыв без связи невозможен.

## Алгоритм и ограничения производительности

Под существующей блокировкой authority выполняется один проход по committed-состоянию.
Bounded priority queue хранит не более limit+1 кандидатов (добавочный — look-ahead).
Только этот небольшой набор сортируется; возвращаемые модели отделены от состояния базы.
Количество совпадений и глобальные статусы вычисляются тем же проходом.
Время O(N log P), дополнительная память O(P), где P<=101, а не полный clone или sort N.

Поиск/подсчёт всё ещё сканируют N записей под блокировкой. Это не B-tree индекс, не SQL
keyset query и не гарантия работы с миллионами записей. При очень частых записях
курсор может часто устаревать; стабильное окно либо экспорт через административный API
предпочтительнее бесконечных автоматических повторов. Общие лимиты базы не сняты.

## Обновление с 0.17.0

Остановить службу; сохранить закрытую согласованную копию authority и server-clock.json;
заменить server, admin и owner-web из новой проверенной сборки; запустить службу;
войти заново и проверить поиск, страницы, карточку и резерв на тестовой лицензии.
Новый init/издатель не нужен. Схема базы не менялась. Основные клиентские ключи,
активации и сроки не сбрасываются. Обязательного обновления клиентской программы
из-за этой серверной пагинации нет. Новый frontend нельзя ставить перед старым backend:
новые endpoints на нём отсутствуют. История API для старого UI сохранена.

Штатные Windows/Linux сборки создаёт scripts/build_license_owner.py. Для клиентской
сборки остаётся build.cmd с собственным публичным client-trust.json. Production HTTPS,
Windows native publish и настоящая игра требуют отдельных приёмочных прогонов.
