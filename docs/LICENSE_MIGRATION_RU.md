# Обновление до 0.19.1

При переходе с 0.19.0 схема базы, issuer, ключи, account и клиентский протокол
сохраняются. На остановленном сервере сделайте закрытую согласованную копию
полного authority и отдельно паролей; замените server/admin/web проверенными
пакетами 0.19.1. Не повторяйте `init` или `web-init`. Запустите единственную службу,
проверьте health, вход, сохранность лицензий и клиентскую активацию/проверку.

Для текущего VPS: [порядок обслуживания](VPS_DEPLOYMENT_RU.md).
Свежие Windows/HTTPS/restart-проверки: [отчёт 0.19.1](VERIFICATION_0.19.1_RU.md).
Ниже сохранена история переходов предыдущих схем; номера старых версий в ней
относятся к соответствующей миграции и не являются текущими путями релиза.

## История: обновление 0.15.0 → 0.16.0

Сделайте закрытую копию authority + master.pass на остановленном сервере. Не выполняйте новый init.
Замените проверенный server/admin, добавьте web/. Схема payload автоматически меняется с 2 на 3;
issuer, лицензии, установки, сроки, отзывы и server-clock.json сохраняются. Резерв по умолчанию выключен.
Создайте web-account через web-init на остановленном сервере; настройте exact HTTPS origin и новый
web-порт по ADMIN_WEB_RU.md. Чтобы пока оставить только CLI, не задавайте --web-root.

Сервер 0.16 понимает прежние корректные online-запросы v1. Старые клиенты без reserve остаются онлайн.
Новый клиент также обычный онлайн до отдельного reserve-enable. Клиент0.16 + server0.15 не поддерживает
резерв: ошибка не превращается в разрешение. Откат только бинарника сервера не поддерживается:
server0.15 не понимает schema3. Для восстановления согласованной резервной копии остановите запись
и учитывайте, что откат может восстановить ранее отозванные права. Не редактируйте checkpoint.

Новые приватные файлы: web-account.json, web-account.lock; у клиента reserve.json. При backup account-файл
содержит TOTP seed и неиспользованные recovery hashes — храните его вместе с issuer закрыто.
Веб-сессии не переживают рестарт и не являются частью backup. Frontend web/ не содержит секретов.

### Обновление сервера лицензий 0.14.0 → 0.15.0

## Совместимость и важное изменение

Публичный API остаётся v1. Выданные ключи, issuer, открытый ключ, даты активации/истечения,
лимиты установок и записи отзыва сохраняются. Новый клиент не требует повторного init.
Обычные запросы старого клиента содержат все обязательные поля и сохраняют совместимость;
неполные/некорректные запросы теперь отклоняются строже.

Внутренний payload базы переходит со schema 1 на schema 2. Внешняя HMAC-оболочка базы
остаётся schema 1. Создаётся обязательный приватный `server-clock.json`.
Не редактируйте его и не пытайтесь снять блокировку удалением файла.

## Порядок обновления владельцем

Сначала соберите и проверьте owner-release 0.15.0 через штатный .NET SDK по LICENSE_OWNER_RU.md.
Не заменяйте production-бинарники диагностическими Roslyn-DLL из тестовой среды.
Сверьте часы VPS и синхронизацию времени. Выберите период, когда клиентские операции можно
приостановить: строгий онлайн-клиент не будет бесконечно работать при остановке authority.

```bash
sudo systemctl stop lsptool-license
sudo systemctl is-active lsptool-license
```

Вторая команда должна показывать inactive/failed, а не active; её ненулевой код здесь ожидаем.
Под закрытыми правами сделайте копию **всего** каталога authority и отдельно файла пароля.
Далее замените каталоги server/admin проверенной сборкой 0.15.0, сохранив конфигурацию и владельцев.
Новый private init выполнять **не нужно**. Пути установки не меняются.

```bash
sudo systemctl start lsptool-license
sudo systemctl status lsptool-license --no-pager
curl --fail http://127.0.0.1:17840/health
```

Затем проверьте свой реальный HTTPS-домен, чтение списка лицензий через закрытый admin API,
одну ранее активированную установку, короткий новый тестовый ключ и отказ после его истечения.
Для исторического комплекта 0.15.0 production HTTPS/Windows не были проверены.
Текущие результаты 0.19.1 приведены в отчёте по ссылке выше.

## Что происходит при первом запуске

Сервер получает эксклюзивную блокировку и проверяет существующую базу и ключ.
Для legacy schema 1 создаёт checkpoint не раньше LastWriteUtc, а затем сохраняет schema 2.
Если checkpoint уже создан, но предыдущая попытка обновления прервалась, его подпись/время
проверяются повторно. Миграция не сбрасывает период тестирования или историю устройств.
После успешного обновления снова сохраните полный согласованный backup.

## Диагностика

| Код | Проверка владельцем |
|---|---|
| SERVER_CLOCK_ROLLBACK | Исправить время VPS; выяснить причину скачка. Не переводить назад и не удалять checkpoint |
| SERVER_CLOCK_MISSING | Для schema 2 восстановить согласованную полную резервную копию, а не создавать пустой файл |
| SERVER_CLOCK_INTEGRITY | Проверить восстановление authority и clock как единого набора, права/носитель |
| DATABASE_INVALID | Отложить обновление, исследовать структуру защищённой копии; не править активную HMAC-базу вручную |
| DATABASE_LIMIT | Проверить объём и лимиты; перенос/архивация требуют согласованной процедуры |

При ошибочном скачке далеко вперёд сервер консервативно сохраняет принятый момент. Нельзя
одновременно обещать защиту от отката и автоматически обнулять защиту при неудобной дате.
Восстановление более раннего полного backup — отдельное решение владельца после анализа
сроков и отзывов; оно может вернуть устаревшее состояние лицензий. Это не защищённая миграция назад.

## Откат версии

Старый сервер 0.14.0 не понимает schema 2. Подмена только бинарников назад не поддерживается.
Храните исходный полный backup до миграции, учитывайте все изменения/активации после него и
не запускайте две authority одновременно. Не восстанавливайте один licenses.json отдельно
от server-clock.json и authority.json. Пароль и приватные данные никогда не идут в клиентский ZIP/Git.

## Обновление 0.19.0: MFA и сессии

См. [изолированную проверку владельца](ADMIN_AUTH_CONCURRENCY_RU.md).
WEB_BUSY — полоса проверки занята; автоматического повтора пароля/кода нет.
WEB_RATE_LIMIT при reauth относится к сессии, а не к IP. WEB_UNAUTHORIZED после
долгой проверки требует нового входа. Исходные лицензии и резерв до 168 часов не меняются.
Не выполнять новый init; обновить согласованный серверный пакет и web, затем войти заново.
