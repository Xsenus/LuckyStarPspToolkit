## Каталоги и границы доступа

| Путь или компонент | Назначение |
|---|---|
| `/opt/lsptool-license/releases/0.19.1/server` | Linux-сборка сервера |
| `/opt/lsptool-license/releases/0.19.1/admin` | Утилита владельца; не публикуется через HTTP |
| `/opt/lsptool-license/releases/0.19.1/web` | Собранные React/JS/CSS/HTML панели |
| `/opt/lsptool-license/current` | Ссылка для удобства оператора; служба использует физические пути релиза |
| `/var/lib/lsptool-license/authority` | Постоянные issuer, лицензии, временной checkpoint, аккаунт владельца |
| `/etc/lsptool-license/master.pass` | Закрытый файл пароля шифрования authority |
| `/var/lib/lsptool-license/operator` | Временная закрытая передача владельцу: enrollment и остальные owner-файлы |
| `lsptool-license` | Системный пользователь и единственная служба приложения |
| `/var/lib/lsptool-acme/config/live/lsptool-domain` | Сертификат домена и приватный ключ для Nginx |
| `/var/lib/lsptool-acme/www` | Webroot HTTP-01 challenge; только файлы ACME-проверки |
| `/opt/lsptool-certbot` | Изолированная установка Certbot 5.4.0 |
| `/etc/nginx/conf.d/lsptool-license.conf` | Виртуальный хост только домена приложения |
| `/etc/nginx/snippets/lsptool-admin-proxy.conf` | Установленный proxy-snippet панели |

Версионированный код не содержит рабочую базу. Обновление приложения не должно
пересоздавать authority, issuer, аккаунт владельца или ключи подписи. Замена issuer
нарушает доверие уже выпущенных клиентов.

Для состояния и секретов используются закрытые каталоги и доступ только нужного
пользователя службы/владельца. Публичные файлы React отделены от `authority`,
`operator`, административного токена и пароля. Не помещайте резервные копии этих
каталогов в webroot или Git.

**Особенность пути `web-root`:** загрузчик намеренно отвергает символические ссылки
во всех предках пути. Передавайте физический каталог
`/opt/lsptool-license/releases/0.19.1/web`, а не `current/web`. При обновлении и откате
одновременно меняются физический путь исполняемого файла и `--web-root` в `ExecStart`.
Путь `--data` и путь `--password-file` остаются постоянными.

## HTTPS и порты

| Внешний путь | Backend | Доступ |
|---|---|---|
| `https://lspt.blagodaty.online/` и `/api/*` | `127.0.0.1:17842` | Панель, cookie, MFA, CSRF |
| `https://lspt.blagodaty.online/v1/*` | `127.0.0.1:17840` | POST-запросы клиентской активации и проверки |
| `https://lspt.blagodaty.online/health` | `127.0.0.1:17840` | GET-проверка доступности |
| `/admin/*` | Нет публичного backend | Ожидается HTTP 404 |
| `127.0.0.1:17841` | Приватный bearer API | Только локальный доступ или закрытый SSH-туннель |

Порты 17840–17842 должны слушать только loopback. Внешняя публикация проходит через
443. На 80 остаются перенаправление на HTTPS и исключение
`/.well-known/acme-challenge/` для продления сертификата.

Используется [nginx-combined.conf](../deploy/licensing/nginx-combined.conf) с заменой
домена и путей сертификата. Это альтернатива двум отдельным шаблонам `nginx.conf` и
`nginx-admin.conf`: не подключайте их одновременно, поскольку они повторяют имена
upstream и зон ограничений. Исходный snippet
[lsp-admin-proxy.conf](../deploy/licensing/lsp-admin-proxy.conf) устанавливается в
`/etc/nginx/snippets/lsptool-admin-proxy.conf`; соответствующие `include` в
виртуальном хосте также заменяются на это имя. Он перезаписывает `X-Real-IP` адресом
фактического клиента. Общий `/etc/nginx/nginx.conf` сохраняется.

Production-origin аккаунта владельца должен точно совпадать с
`https://lspt.blagodaty.online`. Вход по IP или другому домену не заменяет эту
настройку. Проверка сертификата остаётся включённой; `--development-loopback`
предназначен только для локальных тестов.

После изменения только своего виртуального хоста:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Выполняйте reload только после успешного `nginx -t`. Проверка общего Nginx нужна
также для сохранения доступности остальных сайтов.

## Проверки после установки, перезапуска и обновления

На VPS:

```bash
sudo systemctl is-active lsptool-license
sudo systemctl show lsptool-license -p ExecStart -p User -p MemoryCurrent -p MemoryMax
sudo ss -ltnp '( sport = :17840 or sport = :17841 or sport = :17842 )'
curl --fail --silent --show-error http://127.0.0.1:17840/health
sudo nginx -t
```

С отдельного клиентского компьютера, без отключения проверки TLS:

```bash
curl --fail --silent --show-error https://lspt.blagodaty.online/health
curl --fail --silent --show-error --output /dev/null --write-out '%{http_code}\n' https://lspt.blagodaty.online/
curl --silent --output /dev/null --write-out '%{http_code}\n' https://lspt.blagodaty.online/admin/licenses
```

Последняя команда должна вернуть `404`. Проверка `/health` подтверждает только
доступность сервера. Для функциональной приёмки дополнительно нужны:

1. Открытие панели в браузере без ошибок загрузки JS/CSS, вход с паролем и вторым фактором.
2. Просмотр лицензий и журнала; недействительные MFA/CSRF не дают административного доступа.
3. Выдача отдельной тестовой лицензии, активация собранным клиентом, проверка срока и числа установок.
4. Приостановка/отзыв тестовой лицензии с последующей проверкой отказа клиента; ограничение уже выданной краткосрочной lease учитывается согласно [LICENSE_CUSTOMER_RU.md](LICENSE_CUSTOMER_RU.md).
5. Перезапуск службы и проверка сохранения issuer, лицензий и настроек владельца.

Тестовый ключ хранится только в закрытой квитанции и клиентском файле, не в логах
приёмки. Проверка панели не подтверждает запуск изменённых PSP-игр: это отдельная
проверка с оригинальными файлами заказчика.

## Согласованная резервная копия

При приёмке после отзыва тестовой лицензии согласованная tar-копия уже создана
с остановкой и запуском службы. Последующая проверка `/health` вернула HTTP 200;
счётчик перезапусков по сбою `NRestarts` равен нулю. Копия скачана, её SHA-256
сопоставлен с серверным, затем она зашифрована Fernet. Контрольное расшифрование
дало исходные байты архива. Зашифрованный архив, ключ расшифрования и скрипт
восстановления подготовлены как закрытые локальные файлы вне Git; владелец должен
хранить ключ отдельно от архива. Восстановление полной службы на другом сервере
не выполнялось.

База, зашифрованные ключи authority, аккаунт владельца и checkpoint времени должны
попасть в одну согласованную копию. Для небольшого VPS надёжный вариант — короткая
остановка **только** `lsptool-license`. Общий Nginx и чужие службы продолжают работать.
Новые онлайн-проверки лицензий во время остановки недоступны.

Пример из отдельного root-сеанса; архив содержит секреты и предназначен только
для закрытого резервного хранилища:

```bash
set -euo pipefail
backup_dir=/var/backups/lsptool-license
stamp=$(date -u +%Y%m%dT%H%M%SZ)
install -d -m 0700 "$backup_dir"
umask 077
systemctl stop lsptool-license
trap 'systemctl start lsptool-license' EXIT
tar --numeric-owner -C / -czf "$backup_dir/state-$stamp.tar.gz" \
  var/lib/lsptool-license etc/lsptool-license
chmod 0600 "$backup_dir/state-$stamp.tar.gz"
systemctl start lsptool-license
trap - EXIT
systemctl is-active lsptool-license
sha256sum "$backup_dir/state-$stamp.tar.gz"
```

Если создание архива завершилось ошибкой, не считайте оставшийся файл пригодной
копией. Проверьте целостность архива, перенесите его в закрытое хранилище вне VPS
и проверьте доступность восстановления. Отдельно сохраните конфигурацию своей
службы и виртуального хоста; рабочий пароль и authority должны оставаться парой.

Восстановление старой базы может вернуть старые состояния отзыва, привязок устройств
и использованных recovery-кодов. Поэтому обычный откат кода выполняется с текущей
базой. Восстановление состояния из backup — отдельная процедура при потере/повреждении
данных: остановить службу, сохранить повреждённый комплект, восстановить полный
согласованный комплект с владельцем и правами, затем проверить issuer и журнал.
Не смешивайте отдельные JSON-файлы разных дат и не обходите проверку checkpoint.

## Обновление и откат приложения

1. Проверьте SHA-256 нового owner-пакета и свободное место. Распакуйте его в новый
   каталог `/opt/lsptool-license/releases/<version>`, не поверх работающего релиза.
   Linux-файлы `server/lsp-license-server` и `admin/lsp-license-admin` должны иметь
   право исполнения; проверка `--help` не создаёт новый issuer.
2. Сохраните текущий физический путь (`readlink -f /opt/lsptool-license/current`),
   копию своей конфигурации systemd и согласованную резервную копию состояния.
3. Остановите `lsptool-license`. Переключите `current` на подготовленный релиз и
   обновите оба физических пути в `ExecStart`: `server/lsp-license-server` и
   `--web-root` нового релиза. Не меняйте `--data` и `--password-file`.
4. Выполните `systemctl daemon-reload`, затем `systemctl start lsptool-license` и
   проверки из раздела выше. Nginx reload требуется только при изменении его конфигурации.
5. При неудаче остановите только приложение, верните предыдущий `current` и прежний
   `ExecStart`, выполните daemon-reload/start и повторите проверки. Не запускайте
   команды инициализации authority или enrollment при откате.

Откат к старой версии допустим только при совместимой схеме данных. Если новая
версия меняет схему, порядок обратной миграции должен быть установлен до обновления.
Храните предыдущий работающий релиз до завершения проверок; при нехватке диска
переносите старые пакеты в закрытое внешнее хранилище. Не удаляйте чужие каталоги,
рабочую базу или последний пригодный backup ради освобождения места.

## Сертификат и продление

У этого приложения отдельная установка Certbot, чтобы не менять механизм
сертификатов чужих сайтов. Сертификат ожидается в
`/var/lib/lsptool-acme/config/live/lsptool-domain/{fullchain.pem,privkey.pem}`.
Режим продления — webroot `/var/lib/lsptool-acme/www`, поэтому отдельный процесс,
занимающий порт 80, не нужен.

Таймер `lsptool-cert-renew.timer` установлен и активен. Переключение Certbot на
webroot `/var/lib/lsptool-acme/www` и пробное продление успешно проверены.
Установлены два запуска в
сутки, в 00:00 и 12:00 по времени сервера, случайная задержка до 30 минут и
`Persistent=true` для пропущенных запусков. На момент приёмки ближайший запуск
отображался как 12:15 UTC; это снимок расписания, а не постоянное точное время.
Текущий сертификат действителен до **21 декабря 2026 года**. Проверка расписания:

```bash
sudo systemctl list-timers --all lsptool-cert-renew.timer
sudo systemctl cat lsptool-cert-renew.service
sudo journalctl -u lsptool-cert-renew.service -n 50 --no-pager
openssl x509 -in /var/lib/lsptool-acme/config/live/lsptool-domain/fullchain.pem \
  -noout -subject -issuer -dates
```

Служба использует `--config-dir /var/lib/lsptool-acme/config`,
`--work-dir /var/lib/lsptool-acme/work`, `--logs-dir /var/lib/lsptool-acme/logs` и
`renew --cert-name lsptool-domain --quiet`. Пробное продление выполняйте тем же
изолированным исполняемым Certbot и с этими каталогами, добавив `--dry-run`.
Не используйте случайный системный Certbot с другим каталогом конфигурации.
После фактического обновления сертификата deploy-hook должен выполнить `nginx -t`
и лишь затем reload общего Nginx:
`/usr/sbin/nginx -t && /bin/systemctl reload nginx`.
DNS и HTTP-01 маршрут должны оставаться доступны.

## Логи и ресурсы

```bash
sudo journalctl -u lsptool-license -n 80 --no-pager
sudo systemctl show lsptool-license -p ActiveState -p SubState -p NRestarts -p MemoryCurrent -p MemoryHigh -p MemoryMax -p CPUQuotaPerSecUSec
df -h /
sudo du -sh /opt/lsptool-license /var/lib/lsptool-license /var/lib/lsptool-acme
```

Для этой установки подтверждены `MemoryMax=192M` (201 326 592 байта),
`MemoryHigh=160M`, `CPUQuota=75%`. `MemoryCurrent` после запуска составил
34 648 064 байта, около **33 MiB**. Это стартовый замер, а не пиковое потребление
или измеренная пропускная способность. Рост базы, параллельные MFA и обновления
требуют контроля памяти, перезапусков и места на диске.

До установки приложения на корневом разделе наблюдалось около 423 MB свободного
места, после установки изолированного Certbot — около 352 MB. После развёртывания
и завершения приёмки последний замер показал **около 212 MiB**, занято
приблизительно **97% раздела**. Свободного места мало: обновление с сохранением
предыдущего релиза и локальная резервная копия требуют предварительного расчёта
размера и освобождения места либо расширения диска. Автоматическое обновление
приложения без такого контроля не настроено и не заявляется.

Самодостаточные .NET-пакеты, предыдущий релиз, временное извлечение native-библиотек,
backup и журналы занимают дополнительное место; перед каждой операцией нужен
свежий `df`. Ограничение диска сохраняется, даже когда `/health` отвечает успешно.

При повторных падениях изучайте причину через журнал и состояние службы. Не
увеличивайте бесконтрольно лимиты общей машины и не отключайте проверку целостности
базы. В публичный отчёт переносите только очищенные статусы, версии, хеши пакетов и
счётчики; исключайте пароли, токены, ключи клиентов, MFA-seed и recovery-коды.

## Передача владельцу и клиенту

Владелец получает отдельно и закрыто пароль панели, данные подключения, enrollment
для аутентификатора/recovery-коды и инструкции восстановления. Файлы из `operator`
не являются вложениями к публичному GitHub-релизу. После подтверждённого сохранения
в закрытом хранилище владельца удаляется временный enrollment с VPS; рабочие файлы
authority и `master.pass` сохраняются.

Клиент получает клиентскую сборку с публичным trust и свой activation key. Ему не
передаются owner-пакет, bearer-токен, база, master passphrase и квитанция владельца.
В публичном репозитории находятся исходники, документация и шаблоны без приватных
игровых файлов. Подробные операции панели:
[ADMIN_WEB_RU.md](ADMIN_WEB_RU.md),
[LICENSE_OWNER_RU.md](LICENSE_OWNER_RU.md),
[LICENSE_CUSTOMER_RU.md](LICENSE_CUSTOMER_RU.md).
