# Модель защиты лицензирования 0.14.0

## Граница гарантий

Механизм закрывает штатный CLI до получения подписанного онлайн-разрешения и повторяет проверки в долгих операциях.
Это не утверждение о невзламываемом DRM. Пользователь с контролем своего компьютера может модифицировать исполняемый
код, пользоваться ранее выданной сборкой без лицензирования, заменить runtime или вызвать открытые библиотечные API
в изменённой программе. Исходники, тестовые сборки и инструменты владельца клиентам не передаются.
Скрытые значения, упаковка single-file и CNG не считаются гарантией против патчинга.

Существующая MIT LICENSE и сторонние права не меняются добавлением технического контроля. Это не готовый
коммерческий EULA и не отзыв уже предоставленных прав на прежний код. Вопросы происхождения VWF остаются
в THIRD_PARTY_NOTICES.md. Публичный Git с исходниками делает удаление проверки доступным получателю.

## Протокол

Ключ доступа — 256 случайных битов из генератора ОС, с префиксом LSP-. В базе хранится только HMAC-SHA256,
по которому выполняется индексный поиск. Это случайный токен, не человеческий пароль; не заменяйте его короткими кодами.

Перед активацией/проверкой сервер выдаёт challenge, связанный с операцией и установкой. Клиент подписывает
фиксированное доменно-разделённое представление запроса своим P-256 ключом. Challenge одноразовый и живёт 60 секунд.
Ответ подписан приватным ключом владельца; клиент сначала проверяет ECDSA/SHA-256/P1363 подпись, затем issuer,
product, licenseId, deviceId, привязку к ОС, nonce и срок. Алгоритм не выбирается из недоверенного заголовка.
Формат LSP1 не является JWT и не совместим с JWT-валидаторами.

Сервер использует BCL ECDsa; собственная реализация эллиптической криптографии не создавалась.
HTTPS дополнительно защищает конфиденциальность активации. Нет отключения проверки сертификата,
редиректов, fallback на HTTP, trust-файла рядом с EXE или переключателя «не проверять лицензию».
Production build запрещает тестовый loopback trust; временный тестовый издатель компилируется отдельно только в тестах.

## Время, отзыв и сеть

Лицензия — авторитетная запись на сервере. Дата начала задаётся владельцем: выдача или первая успешная активация.
Срок второй установки, повторный ввод ключа и reset-device не обнуляют дату первой активации.
Часы сервера монотонно продвигаются внутри процесса; при запуске время не должно быть заметно раньше последней записи базы.
Полная защита от root на сервере, замены всей базы/снимка VM или подмены NTP не заявляется.

Каждая команда требует нового обмена. Исполняемое разрешение не сохраняется на диск. Максимум разрешения — 120 секунд,
по умолчанию 90, допустимая настройка 15..120. Из времени вычитается длительность сетевого обмена; дальнейший отсчёт
использует Stopwatch. Повторные проверки — не реже обычного интервала до 30 секунд, отдельно работает watchdog
с опросом 200 мс. Это интервалы приложения, а не гарантия планирования потоков ОС или немедленного remote kill.
После недоступности сервера прежний короткий допуск не продлевается; после его окончания работа блокируется.

Явный отказ на проверке прекращает процесс. В других случаях отзыв обнаруживается при следующем обмене или
окончании краткого допуска. Исходные файлы не удаляются. Принудительный выход во время операции не обеспечивает
многофайловой crash-атомарности: могут остаться temp/backup/частично завершённые наборы. Следующий запуск требует
нового допуска, а операции проверяют входные данные заново. Оснований обещать «нулевую задержку отзыва» нет.

## Хранение

Приватный ключ владельца экспортируется в зашифрованный PKCS#8: AES-256-CBC, PBKDF2-HMAC-SHA256,
600 000 итераций, случайная соль платформенного экспортёра. Пароль минимум 16 символов; для службы используйте
генерируемые 48 случайных байт, храните файл отдельно с ограниченными правами. KDF выполняется при инициализации/запуске,
а не на каждом heartbeat. Наличие формата и алгоритма само по себе не означает FIPS-сертификацию.

Windows: пользовательский CNG P-256 с ExportPolicy.None; приватный экспорт API запрещён, но это software KSP,
не подтверждённое TPM-хранилище и не аппаратная аттестация. Новые закрытые каталоги и файлы получают ACL текущего пользователя и LocalSystem; секреты записываются после установки ACL. Windows CNG/ACL в этой среде не запускались.
Linux: программный PKCS#8 в файле 0600, новые каталоги 0700, привязка к хэшу machine-id. Это защита доступа,
а не шифрование от владельца учётной записи/root; копирование VM с ключом и machine-id может клонировать установку.

База аутентифицируется HMAC, запись — приватный temp, flush и rename; отсутствующая/повреждённая база не пересоздаётся.
Первоначальные файлы издателя публикуются переименованием каталога. Единственный писатель удерживает exclusive lock.
Это локальное хранилище одного сервера, не распределённая СУБД/HA. Требуются резервные копии и контроль диска.

## Ограничение ресурсов и оптимизация

- JSON запроса ≤32 КиБ, глубина ≤24; повторные/экранированные дубли и неизвестные свойства запрещены.
- Кэш challenge ≤4096; очередь истечения ограничена и уплотняется, нет полного сканирования на каждый запрос.
- 24 публичных обработчика и 4 зарезервированных административных; независимые бюджеты запросов.
- В процессе: ≤6000 публичных и ≤600 административных запросов/минуту; Nginx отдельно ограничивает IP.
- Снимок данных ≤32 МиБ, лицензий ≤10 000, журнал/UUID повторов ограничены. Проверки не пишут снимок на диск.
- Изменение состояния копирует и аутентифицирует снимок целиком. Это сознательный компромисс небольшой установки;
  пропускная способность больших инсталляций, сети и TLS нагрузочным тестом не подтверждена.
- Клиент повторно использует HttpClient и идентичность; таймаут запроса/чтения тела 8 секунд, серверный body-timeout ограничен.

## Что остаётся эксплуатационной ответственностью

TLS/DNS/сертификат, закрытые owner-токен и passphrase, обновление ОС, NTP, резервные копии, права доступа,
мониторинг сервера, договорные условия тестирования. Нет HSM, аппаратной аттестации, обфускатора/NativeAOT,
автоматической ротации ключей, веб-кабинета, биллинга и кластерного восстановления.
