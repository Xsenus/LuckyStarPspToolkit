# Резерв и сессии владельца · 0.17.0

## Исправленные сценарии

В 0.16.0 обнаружены и воспроизведены одинаковым C#-кодом три случая:
1. Клиент увидел истечение резервного срока, но отказ не записал. После возврата календаря и
   нового запуска тот же сохранённый допуск снова принимался.
2. Отказ из-за перевода часов назад также не переживал исправление календаря и перезапуск.
3. Сброс установки удалял её из лицензии, но не отзывал резерв. Повторная активация той же
   пары ключей позволяла обновлять исторический допуск.

Теперь наблюдённые истечение/откат записываются в подписанное локальное состояние до отказа,
включая `Remaining(false)`. В памяти отказ устанавливается до дисковой записи: сбой диска
не возвращает разрешение параллельному вызову. Снять такой отказ можно только успешно полученным
и проверенным новым серверным допуском — командой `license reserve-enable --id UUID` при связи.
Обычная онлайн-лицензия от этого не отзывается. Удаление файла резерва оставляет клиента без offline-доступа.

Сброс устройства в одной транзакции отзывает все ещё не отозванные допуски этого сочетания
лицензии и установки. Для нового резерва создайте новый grant. Другие лицензии/установки не затрагиваются.
Журнал содержит существующие события `reserve-revoke` и `reset-device`; формат базы не меняется.
Старый disconnected token невозможно отозвать мгновенно: до связи он ограничен подписанным TTL.

## Сессии владельца в React

Раздел **Сессии владельца** показывает текущую и другие браузерные сессии. Это не устройства
клиентов. Показаны независимый UUID управления, возраст, время отсутствия активности.
Cookie и CSRF-токены других сессий не публикуются. UUID управления не принимается при входе.
Можно завершить одну чужую сессию или все остальные. Текущая сохраняется; для неё есть «Выйти».

Отзыв требует текущую cookie-сессию, правильный CSRF и пароль + MFA, подтверждённые не более
пяти минут назад. При необходимости нажмите «Подтвердить вход», затем повторите действие.
Повторный отзыв отсутствующей сессии — безопасная операция с результатом 0.
После отзыва новый запрос с прежней cookie возвращает 401; уже допущенная операция не откатывается.
Просмотр списка не продлевает активность остальных браузеров. Автоопроса, сохраняющего сессию
открытой бесконечно, нет. Сессии по-прежнему теряются после перезапуска backend.

API: GET `/api/sessions`; POST `/api/sessions/revoke` с JSON
`{"sessionId":"UUID_УПРАВЛЕНИЯ","others":false}` либо `{"sessionId":"","others":true}`.
Старый административный bearer API не публикуйте в Nginx.

## Повторные запросы и ограничение памяти

React использует один неизменяемый запрос для одинакового административного действия при
неопределённом результате. Порядок полей не создаёт новый requestId, одновременные одинаковые
нажатия объединяются. Поздний ответ после выхода не удаляет повторный запрос новой сессии.
Автоматических повторов мутаций нет. Квитанции выдачи ключей продолжайте хранить отдельно.

HTTP-ответ читается с лимитом 16 МиБ **в байтах** до разбора JSON, а не проверяется после полного
`response.text()`. Чтение отменяется при превышении лимита. Маленькие фрагменты объединяются
в блоки до 64 КиБ. Некорректный UTF-8 отклоняется. Полный список лицензий пока не заменён
потоковой серверной пагинацией; улучшение ограничено чтением ответов и хвостом журнала.

## Обновление

1. Остановите сервер и сохраните закрытую согласованную копию authority вместе с server-clock.json,
   web-account.json, ключами и отдельным паролем. Не запускайте повторные `init` / `web-init`.
2. Соберите и замените **server и web вместе**: интерфейс 0.17 требует новых endpoint сессий.
   Административные инструменты лучше обновить тем же owner-пакетом.
3. База остаётся схемы 3; ключи, сроки, устройства, MFA и issuer сохраняются.
4. Пересоберите клиент с прежним client-trust.json и передайте новую клиентскую версию.
   Старый клиент 0.16 не получает исправления локального offline-кэша от обновления сервера.
5. После входа выдайте тестовый резерв, сбросьте установку, активируйте снова: старый grant должен
   вернуть RESERVE_REVOKED, новый должен выдаваться отдельно.

Новые поля локального reserve.json читаются 0.17 совместимо со старым кэшем. Старый клиент может
отклонять новый кэш при откате версии: не удаляйте его ради обхода отказа, используйте обновлённый
клиент и свежую онлайн-авторизацию. Если устройство сбрасывалось **до** обновления сервера,
новый код не восстанавливает исторический отзыв автоматически. Проверьте старые допуски и при
необходимости отзовите их или выключите/включите резерв для смены поколения.

## Границы защиты

Это не защита от патча EXE, полного контроля над ОС, клонирования всех приватных файлов или
отката всей VM. Отзыв offline-разрешения виден без связи только по его прежнему сроку (до 168 часов).
Если отказ невозможно сохранить на диске, текущий процесс остаётся заблокированным; абсолютная
долговечность на неисправной/подменённой файловой системе не обещается. Рабочие данные пользователя
не удаляются. Проверка реальных Windows/HTTPS/игры остаётся отдельной приёмкой.
