# Автоматические сборки и релизы 0.13.0

## Единый вход

- Windows: `build.cmd` или `scripts/build.ps1`.
- Linux: `./build.sh`.
- Прямой переносимый вариант: `python scripts/build_release.py`.
- MSBuild: `dotnet msbuild Build.proj -t:Release -p:ReleaseRids=win-x64`.
- Только компиляция и проверки без упаковки: `python scripts/build_release.py --compile-only`.

`--rids win-x64,linux-x64` — значение по умолчанию. `--rids win-x64` выпускает Windows. Обычный build solution в IDE не запускает recursive publish. Пользуйтесь указанными entry points, чтобы получать релизные ZIP автоматически.

## Проверки до упаковки

1. Проверка выбранного стабильного .NET 9 SDK.
2. XML `summary`, параметры, возврат; отдельная проверка полей/свойств/enum; актуальность API reference.
3. Генерация независимых эталонов и Python-валидаторы форматов, репозитория и сохранённых старых customer-отчётов.
4. Python regression tests сборочного механизма.
5. Restore и Release build solution. Ненулевой код немедленно останавливает конвейер.
6. Оба C# self-test проекта, Roslyn-аудит именованных объявлений и self-test CLI.
7. RID-specific self-contained publish с собственным restore. Нельзя добавлять сюда `--no-restore` без заранее выполненного эквивалентного RID restore.
8. Проверка сигнатуры исполняемого файла. На совпадающем с хостом RID — фактический version, self-test, полное synthetic demo.
9. ZIP, SHA-256 и метаданные. Успешная временная папка заменяет предыдущий релиз только после прохождения всех предыдущих стадий.

Любая ошибка до продвижения новой папки не удаляет предыдущий успешный релиз. Два rename с откатом не являются обещанием crash-atomic транзакции при выключении питания. При проблеме удаления backup скрипт сообщает сохранённый путь. Данные игры и шрифты не включаются в релизные пакеты.

## Выходы

`artifacts/releases/<VERSION>/<RID>/`, ZIP и `.zip.sha256`, общий `build-report.json`. Все диагностические логи дополнительно остаются в `artifacts/build-logs/<run-id>`. Пример показывает структуру, не заранее существующий бинарник.

`compiled: true` — компилятор реально завершился с 0. `testsPassed: true` — все обязательные C#-проверки реально вернули 0. `nativeSmokePassed: false` в cross-published пакете означает, что этот EXE здесь НЕ запускался. `gameRuntimeVerified` не становится true по результатам синтетического теста.

## CI и GitHub Release

`ci.yml` собирает/тестирует и публикует пакеты в отдельных Windows/Linux job; файлы доступны в Actions artifacts. `release.yml` на теге повторяет проверку, сверяет VERSION и создаёт draft prerelease только после успеха обеих платформ. `gh` получает `--repo "$GITHUB_REPOSITORY"`, поэтому ему не требуется несуществующий checkout в финальном job. Повторное создание уже существующего тега может требовать удаления неудачного draft или нового тега; скрипт намеренно не перезаписывает опубликованный релиз молча.

Workflow подготовлен, но в среде разработки 0.13.0 не был запущен в GitHub. Первый реальный CI остаётся обязательным. Источники: Microsoft `dotnet publish` documentation и GitHub Actions documentation; точные ссылки указаны в SOURCES.md.

## Зависимости и повторная сборка

Runtime NuGet-пакетов сторонних разработчиков нет. Self-contained сборке нужны Microsoft runtime packs для каждого RID, поэтому `NuGet.Config` включает только официальный nuget.org. Первый restore/publish может потребовать сеть. Python-пакеты предназначены для development/validation. Старые `bin/obj` в checkout разрешены; готовые бинарники нельзя коммитить в source tree.

Сборки C# детерминированные при одинаковых SDK/исходниках/входах. ZIP имеет стабильный порядок и временные метки, но побайтовое совпадение runtime-пакетов между разными SDK/ОС не обещается. Производительность на реальных крупных игровых архивах ещё не измерена.
